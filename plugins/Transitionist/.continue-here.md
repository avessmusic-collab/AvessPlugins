## Previous State: Stage 2 DSP - Phase 4.2 (Parameter Modulation) Complete

4.1's 6-stage serial chain with two additions per architecture.md/plan.md:
(1) reverb freeze/hold - `freeze = smoothstep(throwNorm, 0.90, 1.00)` drives

## Context to Preserve

**Key Decisions (Stage 0, in addition to prior ideation decisions in mockup
history below):**
- Reverb freeze/hold implemented via `juce::dsp::Reverb::Parameters::freezeMode`
  (built-in), ramped via smoothstep across throw 90%-100%, NOT a custom FDN
  reverb (custom FDN retained only as documented fallback)
- Bipolar DJ Filter implemented via TWO always-running `juce::dsp::LadderFilter`
  instances (LPF24 pinned, HPF24 pinned) with a dead-zone (|sweep|<1%) +
  smoothstep crossfade (1%-5%) between a true dry-bypass tap and whichever
  filter matches sweep's sign - avoids any runtime `setMode()` switching and
  its associated click risk
- Dry/wet mix (throw) uses an equal-power (sin/cos) crossfade, not linear,
  because throw simultaneously increases wet-path density/loudness through
  several other mechanisms
- Output Glue and Stereo Width are both fixed internal constants (not
  parameters) - soft-clip drive 1.15, limiter -1.0dB/50ms release, M/S side
  gain 1.35x - preserving the locked 3-parameter contract
- Reverb Modulation (LFO-modulated micro-delay, ~0.15Hz/+-3ms) is the single
  most explicitly "okay to drop" component if it proves hard to tune -
  documented fallback: juce::dsp::Chorus, then no modulation at all
- Tempo sync for `space` uses a 10-step division table (1/32 through whole
  note) with `SmoothedValue`-ramped delay-time changes (~50ms) to avoid
  clicks on division changes; falls back to 120 BPM if host reports no tempo
- 0 samples reported latency - no component in this architecture requires PDC

## 2026-08-27: Bug audit + fixes (mono-bus safety, preset dropdown truthfulness)

Ran a full manual bug audit of the current v3 (6-parameter:
transition/reverb/delay/delaySync/dryWet/volume) implementation, cross-
checked against JUCE source where relevant. Two confirmed bugs fixed and
documented (full writeups in troubleshooting/):

1. **Mono bus aliasing bug (DSP)** - `isBusesLayoutSupported()` was never
   overridden, so despite a code comment claiming "numChannels is
   guaranteed >= 2", JUCE's permissive default let hosts negotiate a mono
   bus, which silently broke the ping-pong delay (`left`/`right` write
   pointers alias the same buffer, discarding the A-channel tap every
   sample). Fixed by adding an explicit stereo-only
   `isBusesLayoutSupported()` override in `PluginProcessor.h/.cpp`.
   See `troubleshooting/dsp-issues/mono-bus-layout-silently-corrupts-pingpong-delay-Transitionist-20260827.md`.
2. **Preset dropdown lied about actual parameter state (GUI)** - an earlier
   uncommitted repaint fix had removed the `findMatchingPresetIndex()` /
   "Custom" fallback logic, leaving the dropdown hardcoded to show "Init"
   on load regardless of real restored/automated parameter values, with no
   resync afterward. Restored `refreshSelectionDisplay()` wired to all 5
   relevant relays' `valueChangedEvent`s (with an `applyingPreset` guard to
   avoid a "Custom" flicker during the bar's own preset recalls). Applied
   to `Source/ui/public/index.html` AND `.ideas/mockups/v5-ui.html` (kept
   in sync). See
   `troubleshooting/gui-issues/preset-dropdown-lies-about-actual-parameter-state-Transitionist-20260827.md`.

**One further finding, NOT yet fixed (needs a design decision, not a
mechanical fix):** `juce::dsp::Reverb`'s built-in `freezeMode` is
internally a hard boolean at `freezeMode >= 0.5` (confirmed via
`juce_audio_basics/utilities/juce_Reverb.h`: `isFrozen()`,
`updateDamping()`, and the unsmoothed `gain` member all snap discretely at
that threshold), NOT the continuous parameter the architecture.md design
assumed when it specified `freezeMode = smoothstep(transitionNorm, 0.90,
1.00)`. This means despite the intended smooth ramp, the reverb's actual
internal character (input gain 0.015->0.0 instantly, damping/feedback
targets jumping between two different formulas, only smoothed ~10ms
internally) snaps at `transition` ~= 95%, rather than gracefully easing in
across the documented 90-100% range. Likely audible as a subtle "seam"
during a slow sweep/automation through that exact point. Options to fix:
(a) accept as a minor, rarely-hit edge case; (b) run two `juce::dsp::Reverb`
instances (one pinned normal, one pinned frozen) and crossfade their
OUTPUTS with our own smoothstep curve, eliminating reliance on the
internal threshold entirely (added CPU cost, real signal-flow change);
(c) narrow/reposition the ramp so the internal snap point falls somewhere
less likely to be swept slowly through in normal use. Deferred pending
user decision - not implemented this session.
