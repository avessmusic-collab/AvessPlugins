## Phase 3.1 Details

**Implemented in `Source/PluginProcessor.h` / `Source/PluginProcessor.cpp`:**
- `feedbackDelayLine` (`juce::dsp::DelayLine<float, Linear>`, max 60ms
  headroom over the 50ms parameter ceiling), `feedbackDampingFilter` (2x
  `juce::dsp::FirstOrderTPTFilter<float>`, lowpass), `feedbackRmsEnvelope`
  (continuous one-pole RMS tracker, 50ms time constant), two
  `juce::SmoothedValue<float>` (20ms ramps) for zipper-free internalGain/
  cutoff changes, `feedbackMaxDelaySamples`, `feedbackCircuitBreakerTripped`
  (diagnostic atomic), `resetFeedbackLoopChannel()` helper. All declared
  before the APVTS `parameters` member per initialization-order convention.
- `prepareToPlay()`: sizes/prepares the delay line and damping filters,
  computes the RMS one-pole coefficient, resets smoothed values.
- `processBlock()`: per-sample loop (dual-mono, channels 0/1) implementing
  `popSample -> [SPLICE: Distortion] -> [SPLICE: Filter] -> damping filter
  -> tanh soft-clamp -> RMS limiter -> isfinite circuit breaker ->
  pushSample -> sum into output`. Both TODO splice points are explicitly
  commented for Phase 3.3/3.4 integration - no throwaway Distortion/Filter
  logic was built. `microDelayTime` binds directly to the delay line's
  `setDelay()` (resolves architecture.md's flagged spec gap).
- Two independent finite-value guards: (1) checks `loopSample` after the
  damping/gain/RMS chain, resetting the channel's delay+filter+RMS state on
  failure (catches corruption generated INSIDE the loop); (2) checks the
  final `x + loopSample` sum before writing to the output buffer (catches a
  non-finite value arriving via the raw host input `x` itself, which guard
  (1) alone would not catch since it only inspects `loopSample`).

**Design choices / open items carried into later phases:**
- `microDelayTime` (parameter-spec.md `Feedback + Delay` module) is bound
  directly as the loop's delay time, per the parameter spec's own note that
  it "resolves architecture.md's previously-flagged spec gap #2" — no
  further decision needed.
- Damping curve: `feedbackDamping` 0-100% maps exponentially to 18000Hz-200Hz
  cutoff (`200 * 90^(1-norm)`), clamped below 0.45x the live sample rate as
  a defensive Nyquist guard for `FirstOrderTPTFilter` stability at
  pathologically low sample rates. Not specified numerically in
  architecture.md - a reasonable interpretation, flag for creative-brief
  confirmation once the loop is audible in Phase 3.4 integration testing.
- RMS limiter threshold 0.95 / 50ms time constant are code constants (no
  bound APVTS parameter, matches architecture.md's description of this as
  an internal safety net, not a user control).
- `feedbackCircuitBreakerTripped` is a diagnostic atomic only - nothing
  reads it yet (no metering/logging UI exists). Available for Stage 3 GUI
  or a future debug build to surface "loop was reset" as a visual indicator
  if desired.

**Validation performed (methodology + limitation):**
This agent session had no Bash/execution tool available (Read/Write/Edit
only - same constraint the Stage 1 foundation-shell-agent session flagged).
No `tests/` directory or Catch2/JUCE `UnitTestRunner` harness exists
anywhere in this repo (checked other plugins, e.g. KICKR - none found), so
per the task's fallback instructions this phase was validated
**analytically/mathematically** rather than by executing a compiled test
harness:

- Per-sample loop gain bound: the only two elements affecting amplitude
  around the recirculation path are the damping filter (a stable one-pole
  TPT lowpass, magnitude response <= 1.0 at every frequency, unity only at
  DC) and `internalGain = 0.85 * tanh(feedbackAmount/100)`. Since
  `tanh(x)` is bounded in [-1, 1] for every finite real `x` (including
  out-of-spec automation edge cases), `internalGain` is bounded in
  [-0.85, 0.85] unconditionally - independent of `feedbackAmount`,
  `feedbackDamping`, or sample rate. At the parameter's actual UI ceiling
  (`feedbackAmount = 100%`), `tanh(1.0) = 0.7616`, so the real worst-case
  per-pass gain is `0.85 * 0.7616 = 0.6474 < 1`.
- Worst case identified per the test criteria (max feedback, min damping):
  `feedbackDamping = 0%` maps to an 18kHz cutoff (near-transparent, gain
  ~1.0 across most of the audible band), so the bounding case reduces to
  the gain analysis above: per-pass loop gain ~0.6474, a contraction
  mapping (ratio < 1). This is a convergent geometric series for ANY finite
  input, at every `feedbackAmount` x `feedbackDamping` combination in the
  full 0-100% x 0-100% range - steady-state output is bounded by
  `x_max / (1 - 0.6474) approx 2.84 * x_max`, finite for any finite input.
  The independent RMS-envelope limiter (0.95 threshold) provides a second,
  unconditional hard ceiling on top of this.
- NaN/Inf recovery: traced every operation in the per-sample chain
  (`tanh`, `std::pow` with a fixed positive base, `FirstOrderTPTFilter`
  with a Nyquist-clamped positive cutoff, multiplication, `std::sqrt` of a
  non-negative accumulator) - none can produce non-finite output from
  finite input under this design. The only realistic NaN/Inf source is a
  corrupted/non-finite sample arriving via the host's `x` input (e.g. a
  misbehaving upstream plugin) or a deliberately-injected test value. Both
  are caught: guard (1) catches corruption already present in
  `loopSample`/loop state; guard (2) catches a non-finite `x` that would
  otherwise leak through `x + loopSample` even after guard (1) resets the
  loop's own state to zero. Both guards fire and recover within the same
  sample they're detected in (bounded to one sample, well within "one
  block").
- No throwaway/temporary debug code was added to the shipped source (no
  execution harness was possible to write given the tool constraint, so
  none needed removing).

**Empirical validation (orchestrator follow-up, completed):** Built
