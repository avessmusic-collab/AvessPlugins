**Component #2 (Distortion Engine, 12 algorithms) —
`processDistortionEngine()`:** manual per-sample switch (NOT
`juce::dsp::WaveShaper`) so the per-algorithm curve, tone-tilt filter, and
DC blocker share one allocation-free code path. `drive` (dB->linear,
smoothed) and `bias` (-100..100 -> +/-0.3 pre-shaper DC offset) applied

final processed output. All 12 algorithms implemented with distinct,
mathematically-correct transfer functions (Saturation=tanh, Soft
Clip=cubic soft-knee, Hard Clip=clamp, Tube=asymmetric tanh, Diode=piecewise
exponential, Fuzz=2-stage hard-clip cascade, Digital Distortion=hard-clip +
fixed 4-bit-style quantizer, Wavefolder=closed-form triangle fold via
`asin(sin())`, Ring-Mod=`x * sine carrier` via a per-channel
`juce::dsp::Oscillator<float>`, Foldback=bounded-iteration reflect-at-
threshold loop). Bitcrusher/Sample-Rate-Reducer choices (indices 7/8) are a
literal no-op passthrough per architecture.md's explicit flagged
resolution (see "Flagged Contradictions/Ambiguities Resolved" below).

**Component #3 (Bitcrusher/SRR, always-on) — `processBitcrusher()`:**
custom sample-and-hold + quantize, `y[n] = quantize(hold(x[n],
srrFactor), bitDepth)` exactly per architecture.md's Algorithm Details
section. `bitDepth` (1-16) -> `levels = 2^bitDepth - 1` (clamped >= 1);
`sampleRateReduction` (1-48) -> integer hold-sample count. Transparent at
defaults (bitDepth=16, srr=1): confirmed by construction (levels=65535,
hold=1 sample = update every sample).

**Component #6 (Filter Stage, 7 topologies) — `updateFilterParameters()` +
`processFilterStage()`:** LP/HP/BP/Resonant LP/Resonant HP via a
per-channel array of `juce::dsp::StateVariableTPTFilter<float>`

Notch via a HAND-ROLLED biquad (manual RBJ notch formula, NOT
`juce::dsp::IIR::Filter::makeNotch()` — see contradiction-resolution note
below); Comb via a per-channel `juce::dsp::DelayLine` + feedback gain
(`filterCutoff` reinterpreted as comb spacing, `filterResonance` as
feedback amount, clamped to 0.92 max). Resonance clamped per-topology
(8.0 ceiling for plain LP/HP/BP, 18.0 for the two "Resonant" variants) to
prevent self-oscillation blowup. Filter state (SVF + Notch + Comb, all
three regardless of which is active) resets on `filterType` change via
`lastFilterTypeIndex` tracking, per architecture.md's explicit requirement.

**Component #14 (Master Mix):** custom two-`SmoothedValue` crossfade (NOT

**Flagged Contradictions/Ambiguities Resolved (all per the task's explicit
instructions to document reasoning either way):**
1. **Output Gain vs. Output Limiter ordering:** architecture.md's component
   #13 prose says "outputGain applied after the limiter", but its own
   "Sequential DSP chain (REQUIRED order)" section lists step 12 Output
   Gain BEFORE step 13 Output Limiter. Resolved by following the Sequential
   DSP chain's explicit numbered order (its own text calls it "REQUIRED"),
   i.e. **Output Gain runs before Output Limiter**. Documented at both the
   header declaration site and the processBlock() call site.
2. **`graphBypassSaturation` vs. `graphBypassWaveshaper`:** determined
   these are NOT redundant/aliased. `graphBypassSaturation` (Distortion
   module's power-icon button) is a whole-module bypass — full dry
   passthrough of the entire Distortion Engine node (drive/bias/tone/mix
   all skipped). `graphBypassWaveshaper` (parameter-spec.md: labelled
   "Fold Bypass", ADV-panel pill toggle) is narrower — it skips ONLY the
   per-algorithm nonlinear transfer function (the `switch` block), while
   drive/bias/tone/distortionMix all remain active. This gives a musically
   useful "clean boosted signal without the waveshaping curve" state,
   distinct from full bypass.
3. **Ring-Mod carrier frequency:** no dedicated APVTS parameter exists for
   this in the locked v2 parameter-spec (architecture.md flags carrier
   freq as a future Mod Matrix destination, not an MVP knob).
   `fold` (0-100%) is repurposed as the carrier-frequency control (20Hz-
   5000Hz exponential) for Ring-Mod specifically, since Fold has no other
   effect on that algorithm. Flagged here per the task's instruction to
   document any such resolution.
4. **Notch filter implementation:** architecture.md recommends
   `juce::dsp::IIR::Filter` with `Coefficients::makeNotch()`, but
   `IIR::Coefficients::make*()` factory functions allocate a new
   heap-backed `Coefficients` object on every call — recomputing every
   block (required, since `filterCutoff`/`filterResonance` are
   automatable) would violate the phase's explicit "no allocation in
   processBlock(), including Notch filter recalculation" requirement.
   Resolved by implementing a hand-rolled biquad using the same underlying
   RBJ notch formula (plain floats, no JUCE `Coefficients` object,
   recomputed every block with zero heap allocation) — functionally
   equivalent transfer function, fully real-time-safe. Same rationale
   applied to the Distortion Engine's tone-tilt filter and DC blocker
   (also hand-rolled one-poles instead of `juce::dsp::IIR::Filter`).

**Validation performed (methodology + limitation):**
This agent session had no Bash/execution tool available (Read/Write/Edit
only - same constraint the Stage 1 foundation-shell-agent session flagged).
No `tests/` directory or Catch2/JUCE `UnitTestRunner` harness exists
anywhere in this repo (checked other plugins, e.g. KICKR - none found), so
per the task's fallback instructions this phase was validated
**analytically/mathematically** rather than by executing a compiled test
harness:

- Per-sample loop gain bound: the only two elements affecting amplitude
  around the recirculation path are the damping filter (a stable one-pole
  TPT lowpass, magnitude response <= 1.0 at every frequency, unity only at
  DC) and `internalGain = 0.85 * tanh(feedbackAmount/100)`. Since
  `tanh(x)` is bounded in [-1, 1] for every finite real `x` (including
  out-of-spec automation edge cases), `internalGain` is bounded in
  [-0.85, 0.85] unconditionally - independent of `feedbackAmount`,
  `feedbackDamping`, or sample rate. At the parameter's actual UI ceiling
  (`feedbackAmount = 100%`), `tanh(1.0) = 0.7616`, so the real worst-case
  per-pass gain is `0.85 * 0.7616 = 0.6474 < 1`.
- Worst case identified per the test criteria (max feedback, min damping):
  `feedbackDamping = 0%` maps to an 18kHz cutoff (near-transparent, gain
  ~1.0 across most of the audible band), so the bounding case reduces to
  the gain analysis above: per-pass loop gain ~0.6474, a contraction
  mapping (ratio < 1). This is a convergent geometric series for ANY finite
  input, at every `feedbackAmount` x `feedbackDamping` combination in the
  full 0-100% x 0-100% range - steady-state output is bounded by
  `x_max / (1 - 0.6474) approx 2.84 * x_max`, finite for any finite input.
  The independent RMS-envelope limiter (0.95 threshold) provides a second,
  unconditional hard ceiling on top of this.
- NaN/Inf recovery: traced every operation in the per-sample chain
  (`tanh`, `std::pow` with a fixed positive base, `FirstOrderTPTFilter`
  with a Nyquist-clamped positive cutoff, multiplication, `std::sqrt` of a
  non-negative accumulator) - none can produce non-finite output from
  finite input under this design. The only realistic NaN/Inf source is a
  corrupted/non-finite sample arriving via the host's `x` input (e.g. a
  misbehaving upstream plugin) or a deliberately-injected test value. Both
  are caught: guard (1) catches corruption already present in
  `loopSample`/loop state; guard (2) catches a non-finite `x` that would
  otherwise leak through `x + loopSample` even after guard (1) resets the
  loop's own state to zero. Both guards fire and recover within the same
  sample they're detected in (bounded to one sample, well within "one
  block").
- No throwaway/temporary debug code was added to the shipped source (no
  execution harness was possible to write given the tool constraint, so
  none needed removing).
