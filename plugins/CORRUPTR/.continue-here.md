**Two real bugs found and fixed in the v5-ui.html mockup itself** (not
present in the mockup-generation contract's C++ scaffolding, only in the
HTML/JS the mockup workflow produced - both violate `troubleshooting/
patterns/juce8-critical-patterns.md`, required reading for this stage, and
were caught by actually launching the built Standalone app and visually
inspecting values, not by code review alone):

1. **Pattern #15 violation (`valueChangedEvent` callback arguments):** every
   one of the mockup's generic `bindKnobs`/`bindFaders`/`bindHSliders`/
   `bindToggles`/`bindPowerButtons` functions wrote
   `state.valueChangedEvent.addListener(n => { value = valueFromNorm(n, ...); })`,
   assuming the callback receives the changed value as an argument. JUCE 8's
   `valueChangedEvent` fires with NO arguments - `n` was `undefined`,
   `valueFromNorm(undefined, min, max)` produced `NaN`, and every bound
   Float slider/fader displayed `NaN dB`/`NaN%`/`NaN Hz` on load (visually
   confirmed via a full-app screenshot before the fix). Fixed by reading
   `state.getNormalisedValue()`/`getValue()`/`getChoiceIndex()` from `state`
   itself inside each listener, matching Pattern #15's documented correct
   form. Also added the missing `state.sliderDragStarted()`/
   `sliderDragEnded()` gesture-bracketing calls (Pattern #23, absent from
   the mockup entirely) to every knob/fader/continuous-hslider drag
   handler, and added previously-missing `valueChangedEvent` listeners to
   `bindModeTiles`/`bindCombos` (mockup had NONE - `distortionAlgorithm`/
   `filterType`/`qualityMode`/`outputLimiterStyle` would not have reflected
   host automation or preset recall back into the UI at all).
2. **Load-time value corruption (proactive `state.setNormalisedValue()`/
   `setChoiceIndex()` push-on-bind):** every one of those same bind
   functions ALSO called `state.setNormalisedValue(normFromValue(value, min, max))`
   (or `setChoiceIndex(index)`) immediately on binding, using the
   `SliderState`'s still-default `{start:0, end:1, skew:1}` properties
   (the real properties/value round-trip from the C++ relay's
   `sendInitialUpdate()` arrives asynchronously and had not landed yet) -
   this WRITES the HTML's local placeholder default straight into the real
   backend/APVTS parameter using the WRONG (default, unskewed 0-1) range
   interpretation, silently corrupting the actual parameter value on every
   plugin load. Confirmed empirically: `filterCutoff` (range 20-20000Hz,
   skew 0.3) loaded clamped to its minimum (20Hz) instead of its true
   20000Hz default; `drive` (0-40dB) loaded at ~0.15dB instead of 6.0dB;
   `inputGain`/`outputGain` (-24..+24dB) loaded at ~0.5dB instead of 0.0dB;
   `mix` (0-200%) loaded at ~1% instead of 100%. (Params whose true default
   happened to coincide with this corrupted computation, e.g. `fold`=0% and
   `filterResonance`=0%, showed no visible symptom - the bug affected EVERY
   bound Float/Choice control, only some were visibly wrong.) **Also
   discovered this corruption persists across app relaunches** via
   `~/Library/Application Support/CORRUPTR.settings` (JUCE Standalone's
   state-save file) - had to be deleted to get a clean re-test after the
   fix. Fixed by REMOVING the proactive push entirely from all 5 affected
   bind functions (`bindKnobs`/`bindFaders`/`bindHSliders` both branches/
   `bindModeTiles`/`bindCombos`) - the local `render()` call still shows the
   HTML placeholder as a brief cosmetic flash before the real backend value
   arrives via the (now-fixed) `valueChangedEvent` listener, but no longer
   OVERWRITES that real value. `bindToggles`/`bindPowerButtons`/
   `bindPerfButtons` did NOT have this bug (they only call `state.setValue()`
   inside their click handlers, never proactively on bind) - left unchanged.

Both fixes are confined to the 8 shared JS binding-helper functions inside
`<script type="module">` in `index.html` - no visual/CSS/layout changes, no
C++ changes beyond the ordinary relay/attachment wiring, and no scope
expansion beyond Phase 5.1's 14 parameters (though the fixes themselves
apply to the shared functions used by ALL future phases' controls too,
since duplicating the buggy pattern per-phase would just re-introduce the
same corruption when 5.2-5.6 wire their own relays).

**PER-SAMPLE OVERSAMPLING CALLS — the core restructuring (HIGHEST RISK):**
`juce::dsp::Oversampling::processSamplesUp()`/`processSamplesDown()` are
called with a 1-SAMPLE-PER-CHANNEL block, ONCE PER BASE-RATE SAMPLE (not
once per host block) — a deliberate, FLAGGED deviation from the "efficient"
batched-whole-block oversampling pattern most examples show. REQUIRED
because the Feedback Routing Path's delay line (`microDelayTime`,
0.1-50ms) can be SHORTER than a host block, meaning sample N's Distortion-
Engine input can depend on sample (N - delaySamples)'s FULLY-COMPUTED
(through Filter Stage) feedback output from EARLIER IN THE SAME BLOCK — a
genuine sample-accurate causal dependency a single batched
up-sample-whole-block pass cannot express without either breaking that
causality or a much more complex two-pass/lookahead scheme. Per-sample
`Oversampling` calls are numerically CORRECT (JUCE's internal FIR/IIR
polyphase filters are continuous/causal — processing 1 sample at a time
produces bit-identical output to a whole block at once, as long as samples
are never skipped/reordered) and fully real-time-safe. The tradeoff is
purely CPU overhead (more function-call/loop overhead per block than one
batched call), an ACCEPTED cost given architecture.md already anticipates
Oversampling as the plugin's single highest CPU cost regardless of batching
strategy, and given correctness (preserving the Feedback Routing Path's
EXACT existing causal semantics, per this phase's own "do not silently
change the rate at which any existing per-sample bookkeeping advances"
constraint) was prioritized over raw efficiency for this MVP.

**Loop restructuring specifics:** the per-sample loop's single per-channel
pass (previously: pop feedback -> Distortion -> Bitcrush -> Glitch ->
Filter -> feedback tap -> Master Mix, all inline per channel) is split into
THREE steps per sample index: (1) a small pre-pass gathering BOTH channels'
dry+feedback sum (`feedbackDelayLine.popSample()` — byte-for-byte the SAME
call, at the SAME point in causal ordering, as before; only its TEXTUAL
position moved into this pre-pass) into a 2-element scratch array; (2) ONE
call to the new `processOversampledDistortionAndBitcrush()` helper
(up-sample -> `factor` x [`processDistortionEngine()` +
`processBitcrusher()`, run IN PLACE on the oversampled block] ->
down-sample, or the direct base-rate path for ECO/1x); (3) the ORIGINAL
per-channel loop, now starting from the oversampled/downsampled output
instead of raw `channelData[n]`, continuing unchanged through
Glitch/Filter/feedback-tap/Master-Mix. Glitch's ring-buffer write, the
Sequencer/Mod-Matrix/LFO/glitch-cycle-counter/RNG-draw-sequence bookkeeping
elsewhere in the loop, and every SmoothedValue's tick rate are ALL
UNCHANGED — none of that bookkeeping's rate/ordering was touched, per this
phase's explicit constraint.

**Rate-dependent internal state (FLAGGED, required since Distortion+
Bitcrush now run at up to 8x the base rate):** the tone-tilt filter's/DC
blocker's one-pole coefficients (previously single base-rate scalars,
`distortionToneLpCoeff`/`distortionDcBlockerR`) are now FOUR precomputed
per-factor variants (`distortionToneLpCoeffByFactor`/
`distortionDcBlockerRByFactor`, computed once in `prepareToPlay()`,
indexed by `activeOversamplingFactorIndex` — zero per-block trig/exp
recompute needed). Bitcrusher's SRR hold-counter uses a new
`bitcrushEffectiveHoldSamples = bitcrushHoldSamples * activeOversamplingFactor`
(holding for N OVERSAMPLED samples reproduces the same musical hold
duration relative to base rate that `sampleRateReduction`'s units
describe) — the bitcrush QUANTIZER itself has no rate dependency and needs
no variant. Ring-Mod's `juce::dsp::Oscillator` carrier is re-`prepare()`d
once per block at the current oversampled rate (confirmed cheap/
allocation-free — `Oscillator::prepare()` only updates an internally-cached
sample-rate value, does NOT regenerate the lookup table baked once by
`initialise()` in `prepareToPlay()`). `driveGainSmoothed`/
`distortionMixSmoothed` still tick EXACTLY ONCE per base-rate sample
(unchanged) — their value is held CONSTANT across all `factor` oversampled
sub-samples within a single base sample, per the "do not change existing
per-sample bookkeeping's rate" constraint.

**Oversampling scope (FLAGGED RESOLUTION for "the nonlinear elements
inside Feedback Routing"):** architecture.md component #12 says
Oversampling wraps "Distortion Engine, Bitcrusher/SRR, and the nonlinear
elements inside Feedback Routing." Phase 3.4's own tap-point resolution
already established the loop's actual implemented "copy of the Filter
stage" is a LINEAR one-pole damping filter (not a second nonlinear
waveshaper), and its RMS-limiter/tanh gain-clamp operate on the
ALREADY-post-Filter-Stage (base-rate, by architecture's own explicit
exclusion) signal — there is no separate nonlinear AUDIO-RATE waveshaping
stage inside the feedback loop distinct from Distortion Engine itself.
architecture.md's Integration Points section clarifies the INTENT:
Distortion + Bitcrush + "the feedback loop's own nonlinear content" must be

implementation satisfies that intent STRUCTURALLY: the feedback tap's
recirculated sample is summed into the Distortion Engine's input BEFORE the

RMS-limiter machinery was built (that machinery correctly stays at base
rate, downstream of Filter Stage's real, base-rate output, consistent with
Filter's explicit exclusion from the wrapper).

triplet convention `RhythmicSequencer`'s `kSequencerRateBeats` already
established), then converted to Hz via a THIRD independent, per-block
`AudioPlayHead::getPosition()`/`getBpm()` read (the same cheap,
allocation-free, real-time-safe pattern Phase 3.5's `glitchHostBpm` and Phase
3.7's sequencer-sync read each already independently establish — not a new
mechanism). Chosen because no dedicated division parameter exists in the
locked spec for this MVP; a common, defensible pattern (several commercial
synths/effects use a single Rate knob + Sync toggle this way).

**The 4th random-family shape ("Random," distinct from "S&H") (FLAGGED
DESIGN RESOLUTION):** architecture.md explicitly defines S&H ("hold value
until phase wraps"), Smooth Random ("S&H target with SmoothedValue ramp
between targets"), and Random Walk ("accumulate small random deltas each
wrap") — but never defines plain "Random," the 4th of the 9 shapes. This
implementation resolves it as: a fresh random TARGET drawn on the same
once-per-cycle cadence as S&H, but the OUTPUT ramps LINEARLY from the
previous target to the new one across the cycle's own phase (completing
exactly at the next wrap) — a phase-tied glide, distinct from S&H's hard
step AND from Smooth Random's FIXED-wall-clock-time-constant glide (Random's
glide duration scales with the LFO's own rate; Smooth Random's does not).

**Envelope Follower / Audio Level sources — tap point (FLAGGED) + the
concrete Envelope-vs-Audio-Level distinction:** both source names map to
`juce::dsp::BallisticsFilter<float>` per architecture.md's own suggested
JUCE class, tapping the SAME mono-summed signal, tracked at AUDIO RATE
(once per sample, inside the merged per-sample loop, since BallisticsFilter
is designed for per-sample ballistics unlike this phase's own control-rate
LFOs) — but with DIFFERENT ballistics settings, which is the concrete,
audible difference between the two: `envelopeFollowerBallistics` uses
musical ~10ms attack/~150ms release (a typical envelope-follower feel);
`audioLevelBallistics` uses fast ~1ms attack/~30ms release (near-
instantaneous level tracking). TAP POINT: architecture.md does not specify
one — post-Input-Gain (the conventional choice for an envelope-follower mod
source) is used, flagged. Each block's Mod Matrix resolution consumes the
LAST tracked sample from the PREVIOUS block (`envelopeFollowerLastValue`/
`audioLevelLastValue`) — a standard one-block-old envelope tap, which also
removes any same-block ordering dependency between the per-sample loop
(runs LATE in `processBlock()`) and `resolveModMatrixAndMacroContributions()`
(runs EARLY).

**Mod Matrix's "Sequencer" source + call-order resolution (FLAGGED DESIGN
RESOLUTION):** this is the Mod Matrix's OWN generic tap into the Rhythmic
Sequencer's pattern data, SEPARATE from the Sequencer's 10 pre-wired fixed
lanes (Phase 3.7) — architecture.md doesn't specify which lane (if any
specific one) should feed this generic source choice; this implementation
reuses the Drive lane's raw value as a representative general-purpose
reading. Like Envelope/Audio Level above, this reading is deliberately
ONE-BLOCK-OLD (uses `sequencerLastStepIndex` as resolved by the PREVIOUS
block's `updateSequencerStepAndContributions()` call) specifically so that
`resolveModMatrixAndMacroContributions()` can run BEFORE

with `macroContributions` already resolved for the current block, avoiding
a circular same-block dependency entirely.

**MIDI CC source (FLAGGED DESIGN RESOLUTION):** no per-slot "which CC

## Phase 3.7 Details

**Files created:** `plugins/CORRUPTR/Source/dsp/RhythmicSequencer.h`
(new, header-only, no CMakeLists.txt change needed — same precedent as
`dsp/ModulationAccumulator.h`, included directly by PluginProcessor.h).

**`RhythmicSequencer` class — live representation vs. serialization
(FLAGGED DESIGN RESOLUTION):** architecture.md's Stage 0 decision requires
sequencer pattern data to be "custom `juce::ValueTree` state, NOT
individual APVTS parameters." This implementation satisfies that
requirement at the SERIALIZATION boundary (`toValueTree()`/
`fromValueTree()`, called only from `getStateInformation()`/
`setStateInformation()`) rather than making a live `juce::ValueTree` tree
of per-step nodes the day-to-day editable representation. The LIVE
representation (`workingPattern`) is a plain fixed-size
`std::array<std::array<float,32>,10>`-based POD struct
(`PatternSnapshot`) — simpler to mutate correctly for 10 pattern
operations (no ValueTree property-lookup overhead per edit) and trivially,
cheaply copyable for the double-buffered audio-thread snapshot mechanism,
while `toValueTree()` still produces a genuine `juce::ValueTree` for the
actual persisted-state contract architecture.md describes (a CSV-string
`values` property per lane, nested under a `SequencerPattern` root with a
`version` attribute).

**Double-buffered lock-free snapshot (architecture.md Thread Boundaries:
"double-buffered ValueTree snapshot, pointer swap, same pattern as
DrumRoulette's sample-buffer swap"):** two preallocated `PatternSnapshot`
members (`bufferA`/`bufferB`, sized at construction, never resized) plus
an `std::atomic<PatternSnapshot*> activeSnapshot`. The message thread owns
`workingPattern` (every editing method — `setStep`, all ten `opXxx`
operations, `fromValueTree` — mutates it directly); `publishSnapshot()`
copies it into whichever buffer is currently inactive, then atomically
swaps `activeSnapshot`. The audio thread calls ONLY
`getActiveSnapshot()` (a single relaxed atomic load, real-time-safe) via
`CORRUPTRAudioProcessor::updateSequencerStepAndContributions()`. A public
`getRhythmicSequencer()` accessor (message-thread only, same convention as
the existing `getAPVTS()`) exposes the class directly to a future GUI
rather than adding ~10 forwarding wrapper methods on the processor.

**Message-thread pattern-operation RNG (`editRandom`, inside
`RhythmicSequencer`):** used exclusively by `opRandom`/`opMutate`/
`opSyncopate`/`opHumanize`. Deliberately a SEPARATE `juce::Random` instance
from the audio-thread `glitchRandom` (Phase 3.5) — per this phase's
explicit task instruction to preserve `glitchRandom`'s draw-sequence
determinism invariant unchanged. Unlike `glitchRandom`, this RNG's seed is
NOT persisted: the RESULTING pattern data itself round-trips exactly via
`toValueTree()`/`fromValueTree()`, so a reproducible RNG *stream* isn't
needed here the way it is for Glitch's continuously-drawn, never-directly-
saved chaos jitter.

**Host sync + no-transport fallback
(`updateSequencerStepAndContributions()`, called once per block, before
the Phase 3.2/3.7 drive-accumulate block):** uses the same JUCE 8
`AudioPlayHead::getPosition()` `std::optional<PositionInfo>` API Phase 3.5
already established for `glitchHostBpm` (here reading `getIsPlaying()` +
`getPpqPosition()` instead of `getBpm()`) — a second, independent call to
the same established API/pattern (not a different mechanism; both queries
are cheap/allocation-free so calling `getPosition()` twice per block is
harmless). `sequencerRate`'s 7 choices convert to a fraction-of-a-quarter-
note (beats): 1/4=1.0, 1/8=0.5, 1/16=0.25, 1/32=0.125, 1/4T=0.6667,
1/8T=0.3333, 1/16T=0.1667 (triplet = 2/3 of the equivalent straight
division). Step index = `floor(ppqPosition / stepLengthBeats) mod
numSteps`. **NO-TRANSPORT FALLBACK, verified as an explicit branch (not an
accidental fallthrough):** if there's no `AudioPlayHead`, no
`PositionInfo`, `isPlaying()` is false, or the host doesn't report
`ppqPosition`, `transportValid` stays false and the sequencer explicitly
sets `stepIndex = 0` — architecture.md's "freeze at step 0 / hold last
value" phrasing offers two options; freeze-at-step-0 was chosen as the
simpler, unambiguous, easily user-verifiable one (flagged per this file's
established precedent for such resolutions).

**PER-BLOCK (not per-sample) step-boundary resolution (FLAGGED DESIGN
RESOLUTION — architecture.md doesn't specify granularity):**
`updateSequencerStepAndContributions()` runs exactly once per
`processBlock()`, unlike Phase 3.5's Glitch Engine cycle counter (which
advances per-sample from a per-block BPM read). Reasoning: (1) even the
fastest division (1/32T) at realistic tempos is many samples long relative
to a typical block size, so a step boundary landing mid-block is rare and
its audible impact is already bounded by the existing per-destination
`SmoothedValue` ramps each consumed lane feeds into; (2) matches this
file's OTHER established per-block-cache convention for "discrete,
changes-are-relatively-rare" state (`glitchMode`/`filterTypeIndex`
change-detection), rather than the per-sample-counter convention reserved
for the Glitch Engine's own continuously-recirculating, self-timed cycle
state; (3) plan.md's test criterion ("steps advance correctly synced to
host tempo/PPQ at all 7 rate divisions") doesn't require sample-accurate
placement, only correct tempo/PPQ sync, which per-block resolution still
satisfies (the step index is computed directly from the host's live
`ppqPosition` every block, not a free-running counter that could drift).

**Destination wiring — "Sequencer output enters parameter modulation ONLY
through `ModulationAccumulator::accumulate()`" (task requirement):** every
lane's raw step value (bipolar -1..+1, except Gate which is unipolar 0..1)
is converted to a destination-units contribution scalar in
`updateSequencerStepAndContributions()`, then combined via `accumulate()`
AT each destination's own existing per-block parameter-read call site
(pure insertions, matching this file's established per-phase editing
convention):
- **Drive:** the Phase 3.2 block (renamed/updated in place) — REPLACES the
  synthetic sequencer sine with `sequencerDriveContributionDb`; Mod
  Matrix stays a synthetic stand-in (Phase 3.8), macro/performance-trigger
  terms unchanged from Phase 3.2. Result now CONSUMED by
  `driveGainSmoothed`'s target (previously diagnostic-only).
- **Mix, Filter Cutoff, Bit Depth, Sample Rate Reduction:** Phase 3.3's
  existing per-block parameter-read call sites, each wrapped in a new
  `ModulationAccumulator::accumulate(baseParam, sequencerXContribution,
  0.0f, 0.0f, false, 0.0f, rangeMin, rangeMax)` call (Mod Matrix/Macro/
  Performance Trigger stubbed at 0/false until Phase 3.8/3.9, same pattern
  Phase 3.2 established).
- **Glitch Probability:** Phase 3.5's existing per-block

**Per-lane modulation-depth scaling (FLAGGED DESIGN RESOLUTION —
architecture.md doesn't specify depth per lane):** two conventions,
documented at `updateSequencerStepAndContributions()`'s definition: (a)
lanes with a pre-existing base APVTS knob (Drive/Mix/Filter
Cutoff/Bit Depth/Sample Rate Reduction/Glitch Probability) scale by
`kSequencerModDepthFraction` (0.5) of the destination's full range, so the
sequencer can swing the result up to +/-50% of the range around the
user's own base setting without ever fully overriding it; (b)
Volume/Gate (new, sequencer-owned destinations with no competing base)
use their full range instead.

**Pattern operations (all message-thread-only, all auto-publish via
`publishSnapshot()` at the end — unlike `setStep()`'s batched-editing
contract, these are typically a single discrete user action):** Clear
(reset active steps to each lane's default/"no modulation" value);
Random (fresh uniform-random value per step, full lane range); Mutate
(bounded random nudge, default +/-25% of lane range, clamped back into
range — gentler than Random); Reverse (whole-pattern time-reversal, swaps
step order); Mirror (overwrites the second half of the active window with
a palindrome copy of the first half — distinct from Reverse); Shift
(circular shift by N steps, wrapping within the active window); Half
(stretches the first numSteps/2 steps across the whole window,
nearest-neighbour hold — halves perceived rhythmic resolution); Double
(inverse of Half — samples every other step, spreads across the full
window — doubles perceived resolution); Syncopate (per-adjacent-pair
Bernoulli-trial swap, default 30% probability, introduces off-grid
accents); Humanize (subtle jitter, reuses Mutate's math at a gentler
default depth, 8% vs. Mutate's 25%). architecture.md names these
operations without numerically defining most of them — every numeric
choice above (fractions, probabilities, the Half/Double/Mirror/Shift
transformation shapes themselves) is this implementation's own resolution,
flagged per this file's established precedent.

**State persistence (extends Phase 3.5's custom-state mechanism, per
architecture.md's State Persistence section: "nested `juce::ValueTree`
merged into the same state blob... following the DrumRoulette pattern"):**
`getStateInformation()` calls `rhythmicSequencer.toValueTree()`, converts
to XML, and appends it as a CHILD element of the APVTS state's root
element (alongside Phase 3.5's `glitchRandomSeed`/`corruptrStateVersion`
attributes on that same root — a full nested child element for the
Sequencer's much larger structured data, vs. a plain attribute for
Glitch's single int64 seed, matching architecture.md's DrumRoulette-
pattern description precisely now that the state is large/structured
enough to warrant it). `setStateInformation()` looks up the
`SequencerPattern` child element by name and calls
`rhythmicSequencer.fromValueTree(...)`; if absent (e.g. a preset saved
before this phase existed) or malformed, `fromValueTree()`'s own internal
validity check falls back to the default empty pattern (all lanes at
their "no modulation" default — 0.0 bipolar, 1.0 for Gate) per
architecture.md's Restore Behavior ("never crash on malformed preset
data") — a partially-corrupt preset restores as much of the real pattern
as possible (per-lane/per-step), not an all-or-nothing discard.

**IMPLEMENTATION DEVIATION FLAGGED - Tape Stop/Tape Start/Pitch Jump do NOT
use `juce::dsp::DelayLine`:** plan.md's Components list for this phase
names `juce::dsp::DelayLine` (Lagrange3rd) as the fractional-rate-read
mechanism. This implementation instead uses a hand-rolled 4-point,
3rd-order Lagrange interpolator (`readGlitchRingBufferFractional()` - the
exact same closed-form cubic-Lagrange formula
`DelayLineInterpolationTypes::Lagrange3rd` implements internally) reading
directly from the already-captured, static `glitchRingBuffer` at an
arbitrary fractional index. Reasoning: `juce::dsp::DelayLine`'s API models
"continuously push live input, pop back after a settable delay TIME" - it
has no "seek/scrub to an arbitrary position within an already-captured
static buffer" operation, which is exactly what these three modes need
(their read position is a function of ELAPSED TIME within the event,
computed in closed form, not a fixed/slowly-drifting delay time). Bridging
into DelayLine's push model would require copying `glitchRingBuffer`'s
content into a second buffer every sample - wasted work, a second
real-time-unsafe sizing question, for zero interpolation-quality benefit
over reading the identical 4-point-Lagrange formula directly. The resulting
interpolation ORDER matches plan.md's named component exactly; only the
delivery mechanism differs. `juce::dsp::WindowingFunction` (Granular
Repeat) remains genuinely in use as specified.

**Tape Stop/Tape Start ramp math (click-free-at-ramp-start/end, plan.md
test criterion):** rather than accumulating a per-sample rate multiply
(which would need extra per-channel-call-ordering-sensitive state), the
read position is computed as the CLOSED-FORM INTEGRAL of a linear rate ramp
over elapsed samples within the current cycle (`elapsed`, derived from the
already-shared `glitchCurrentCycleLengthSamples`/`glitchCycleSampleCounter`
- no new per-sample accumulator needed, and independently/identically
computable by each channel's call): Tape Stop `rate(t)=1-t/T ->
position(t)=t-t^2/(2T)`; Tape Start `rate(t)=t/T -> position(t)=t^2/(2T)`
(T = the event's captured window length = the full cycle length for these
two modes). This is mathematically identical to accumulating
`position += rate` every sample from t=0, but is exactly reproducible/
stateless and C1-continuous (both position AND its derivative are
continuous functions of t) - which is what makes the ramp genuinely
click-free, not just "no instantaneous jump" but "no instantaneous jump in
the rate of change either." Both formulas reach `T/2` at `t=T` (the ramp
only ever traverses half the window's nominal length over its full run,
since it spends the other half decelerating/accelerating) - a designed
consequence of the linear-rate assumption, not a bug.

## Phase 3.5 Details

**Ring buffer (`glitchRingBuffer`, stereo `juce::AudioBuffer<float>`):**
allocated once in `prepareToPlay`, sized per architecture.md's "4 bars at
slowest supported tempo" guidance (`kGlitchMinSupportedBpm` = 40bpm, 4/4 time
assumption) computed against the ACTUAL prepared sample rate (not a hardcoded
192kHz), plus one block's headroom. Written continuously with the incoming
post-Bitcrush signal every sample, regardless of whether a glitch is active or
`graphBypassGlitch` is on (architecture.md: "so there's always a recent-
history window available to capture from when a trigger fires"). Never
resized/reallocated in `processBlock()`.

**Trigger mechanism:** a free-running per-sample cycle counter
(`glitchCycleSampleCounter`) whose period derives from `glitchBufferLength`
(1/64..4 bars) converted to samples via host BPM
(`AudioPlayHead::getPosition()->getBpm()`, JUCE 8 `std::optional` API;
falls back to 120bpm with no host/no tempo info, real-time-safe, no
allocation in the fallback path). At every cycle boundary, a Bernoulli trial
(seeded `glitchRandom`, gated by `glitchProbability`) decides whether an
event fires. NOT phase-locked to the host's bar/beat grid - a deliberate
scope simplification (architecture.md only specifies BPM-derived sample-count
conversion, not PPQ phase-locking), flagged as a reasonable interpretation.

**Chaos formula (exact):**
```
chaosNorm = chaos% / 100
probJitter   = (2*rand()-1) * chaosNorm * 0.3   (+/-30% of probability at chaos=100%)
lengthJitter = (2*rand()-1) * chaosNorm * 0.5   (+/-50% of cycle length at chaos=100%)
effectiveProbability = clamp01(glitchProbability%/100 + probJitter)
thisCycleLength = clamp(nominalCycleLengthSamples * (1 + lengthJitter), 1, ringBufferCapacity - 4)
```
Both jitter draws + the Bernoulli draw happen from `glitchRandom`
UNCONDITIONALLY every cycle boundary, regardless of `glitchMode`/
`graphBypassGlitch` - the RNG draw sequence depends only on tempo/sample-
rate/probability/chaos, never on mode selection or bypass state.

**RNG seeding + persistence (architecture.md: "must use a seeded
juce::Random instance... seed stored in custom state"):** `glitchRandom` is a
private, non-global `juce::Random` member. `juce::Random::getSystemRandom()`
is used exactly ONCE, in the constructor (message thread, one-time entropy
source), to generate the initial seed stored in
`glitchRandomSeedAtomic` (`std::atomic<juce::int64>`). `prepareToPlay` and
`processBlock` (once per block, per architecture.md's Thread Boundaries
convention "read once per relevant trigger event, not per-sample") apply
this atomic's current value to the real `glitchRandom` instance whenever it
changes. Persistence: `getStateInformation` writes the seed as a String XML
attribute (`glitchRandomSeed`, full int64 precision - `XmlElement`'s integer
attribute API is 32-bit only) plus a `corruptrStateVersion` attribute onto
the APVTS state's root element (not a second nested ValueTree - sufficient
at this phase's scope, matches architecture.md's "version attribute... from
day one" advice); `setStateInformation` restores it into the atomic (missing/
corrupt attribute -> fresh system-RNG seed, never crashes, per
architecture.md's Restore Behavior). **How a user reloading a saved preset
gets identical glitch timing:** the exact same seed value round-trips through
save -> XML attribute -> load -> atomic -> next block's `glitchRandom`
reseed, so the sequence of Bernoulli-trial/jitter draws from that point
forward is bit-for-bit identical across sessions - the RNG STREAM is
reproducible; exact wall-clock/transport-position alignment of those draws
still depends on where playback starts, same as any tempo-synced effect.

**Per-mode window semantics + design differentiation:** Stutter = short
slice (1/8 of cycle length) captured once, looped forward. Repeat = full
cycle-length window captured once, looped forward. Reverse = full window,
read back-to-front every pass. Freeze = very short (~15ms, "single-cycle"
approximation) window captured once, looped forward. Silence = hard-gated
mute (`readGlitchWindowSample` returns 0.0f), no ring-buffer read. Retrigger
= short slice (1/4 of cycle length) but, UNLIKE Stutter/Repeat, RE-CAPTURED
fresh from the current ring-buffer write position at the start of EVERY loop
pass rather than held fixed for the whole event - a deliberate design

together without specifying what distinguishes them) giving Retrigger a

per the task's fallback instructions this phase was validated
**analytically/mathematically** rather than by executing a compiled test
harness:

- Per-sample loop gain bound: the only two elements affecting amplitude
  around the recirculation path are the damping filter (a stable one-pole
  TPT lowpass, magnitude response <= 1.0 at every frequency, unity only at
  DC) and `internalGain = 0.85 * tanh(feedbackAmount/100)`. Since
  `tanh(x)` is bounded in [-1, 1] for every finite real `x` (including
  out-of-spec automation edge cases), `internalGain` is bounded in
  [-0.85, 0.85] unconditionally - independent of `feedbackAmount`,
  `feedbackDamping`, or sample rate. At the parameter's actual UI ceiling
  (`feedbackAmount = 100%`), `tanh(1.0) = 0.7616`, so the real worst-case
  per-pass gain is `0.85 * 0.7616 = 0.6474 < 1`.
- Worst case identified per the test criteria (max feedback, min damping):
  `feedbackDamping = 0%` maps to an 18kHz cutoff (near-transparent, gain
  ~1.0 across most of the audible band), so the bounding case reduces to
  the gain analysis above: per-pass loop gain ~0.6474, a contraction
  mapping (ratio < 1). This is a convergent geometric series for ANY finite
  input, at every `feedbackAmount` x `feedbackDamping` combination in the
  full 0-100% x 0-100% range - steady-state output is bounded by
  `x_max / (1 - 0.6474) approx 2.84 * x_max`, finite for any finite input.
  The independent RMS-envelope limiter (0.95 threshold) provides a second,
  unconditional hard ceiling on top of this.
- NaN/Inf recovery: traced every operation in the per-sample chain
  (`tanh`, `std::pow` with a fixed positive base, `FirstOrderTPTFilter`
  with a Nyquist-clamped positive cutoff, multiplication, `std::sqrt` of a
  non-negative accumulator) - none can produce non-finite output from
  finite input under this design. The only realistic NaN/Inf source is a
  corrupted/non-finite sample arriving via the host's `x` input (e.g. a
  misbehaving upstream plugin) or a deliberately-injected test value. Both
  are caught: guard (1) catches corruption already present in
  `loopSample`/loop state; guard (2) catches a non-finite `x` that would
  otherwise leak through `x + loopSample` even after guard (1) resets the
  loop's own state to zero. Both guards fire and recover within the same
  sample they're detected in (bounded to one sample, well within "one
  block").
- No throwaway/temporary debug code was added to the shipped source (no
  execution harness was possible to write given the tool constraint, so
  none needed removing).
