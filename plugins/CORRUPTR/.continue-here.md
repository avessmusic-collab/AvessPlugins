## Phase 3.6 Details

adds ZERO new ring buffers, ZERO new trigger/cycle-boundary mechanisms.
`glitchRingBuffer`, `glitchRingWritePos`, the cycle-boundary Bernoulli-trial

pattern - see below - with zero Tier-1 case-1/2/3/5/12/13 behavior changed).
The `isTier1PlayableMode` gate at the Phase 3.5 trigger call site (inside
`processBlock()`'s per-sample cycle-boundary block) was renamed
`isImplementedMode` and widened from an explicit 6-value OR-chain to
`glitchModeIndex >= 1 && glitchModeIndex <= 17` (all 17 non-Off indices are
now contiguous and implemented, so the range check is both correct and
simpler than the old enumeration).

**`readGlitchWindowSample()` restructuring:** now dispatches FIRST to five
Tier-2-specific paths (Granular Repeat -> `readGlitchGranularSample()`; Tape
Stop/Tape Start/Pitch Jump -> `readGlitchFractionalRateSample()`; Slice/
Random Slice -> `readGlitchSliceSample()`; Random Repeat ->
`readGlitchRandomRepeatSample()`; Noise Burst -> an inline per-sample
`juce::Random` draw), THEN Silence's existing `return 0.0f`, THEN falls
through to the ORIGINAL Tier-1 per-channel captured-window loop-read code
(unchanged: `glitchWindowReadPos[channel]`, the Retrigger re-capture branch,
the reverse-direction ternary, the per-loop-pass linear fade) - which now
ALSO serves Buffer Repeat (4) and Micro Loop (8) unmodified (they only need
a different window LENGTH, set in `setUpGlitchEventForThisCycle`) and
Bitcrush Burst (15) with one extra quantize line appended after the fade.
This is a pure widening of the dispatch, not a rewrite of Tier-1's read
math - Stutter/Repeat/Reverse/Freeze/Retrigger/Silence's sample-for-sample
behavior is unchanged.

**Per-mode window-size/behavior decisions (architecture.md does not
numerically differentiate several of these modes from each other -
"replay a captured window repeatedly" describes Stutter/Repeat/Retrigger/
Micro Loop/Buffer Repeat collectively without pinning down relative sizes;
resolutions below are this implementation's own, flagged per this file's
established precedent):**
- **Buffer Repeat (4):** captured ONCE (fixed, non-re-selecting - like
  Stutter/Repeat), `kGlitchBufferRepeatFraction` = 1/2 of the cycle length -
  a moderate chunk sized between Stutter's 1/8 and Repeat's full window.
- **Micro Loop (8):** captured ONCE, `kGlitchMicroLoopFraction` = 1/16 of
  the cycle length - finer-grained than Stutter (1/8), and, unlike Freeze's
  fixed-15ms window, TEMPO-RELATIVE (scales with `glitchBufferLength`).
- **Slice (6) / Random Slice (7):** the full captured cycle-length window
  is subdivided into `kGlitchSliceCount` = 8 equal slices. Slice plays them
  in natural order (0,1,2...7,0,1,2...), looping. Random Slice shuffles the
  play order ONCE at event trigger (Fisher-Yates, seeded `glitchRandom`)
  then holds that fixed shuffled sequence for the rest of the event -
  deliberately NOT re-shuffled every pass, which would read as continuous
  randomization rather than a single "sliced rearrangement" character.
- **Random Repeat (17):** same window SIZE as Buffer Repeat
  (`kGlitchBufferRepeatFraction`), but re-selects a brand-new RANDOM
  historical position (bounded to stay within already-written ring-buffer
  history relative to the CURRENT write position) every time the loop
  wraps - the differentiator from both Buffer Repeat (fixed window, never
  re-selects) and Tier-1's Retrigger (re-syncs to the CURRENT write
  position specifically, not a random historical offset).
- **Granular Repeat (9):** `kGlitchGranularVoiceCount` = 3 fixed,
  round-robin-spawned overlapping grain voices, each
  `kGlitchGrainLengthMs` = 45ms - a FIXED length independent of
  `glitchBufferLength`, deliberately chosen so the Hann window table can be
  sized and filled exactly ONCE in `prepareToPlay()` (real-time-safety-
  motivated scope simplification, flagged). Each grain's start position is
  a fresh random offset within the captured window, drawn from
  `glitchRandom` at the moment that specific grain spawns.
- **Noise Burst (14):** `juce::Random`-generated white noise, drawn
  PER-SAMPLE, PER-CHANNEL independently (stereo-decorrelated), scaled by a
  fixed `kGlitchNoiseBurstAmplitude` = 0.6 constant - NOT matched to the
  live input signal's level (MVP simplification, flagged); the ring buffer
  is not read for this mode at all.
- **Bitcrush Burst (15):** reuses the SAME captured-window loop-read path
  as Buffer Repeat/Repeat (full cycle-length window), then applies one
  extra fixed-depth quantize step (`kGlitchBitcrushBurstLevels` = 7.0,
  ~3-bit) to the already-read sample. Deliberately self-contained to the
  Glitch Engine - does NOT read or write Component #3's `bitDepth`/
  `sampleRateReduction` state, per this phase's explicit task instructions.
- **Pitch Jump (16):** see "Fractional-rate reads" below for the interval
  set decision.

**IMPLEMENTATION DEVIATION FLAGGED - Tape Stop/Tape Start/Pitch Jump do NOT
use `juce::dsp::DelayLine`:** plan.md's Components list for this phase
names `juce::dsp::DelayLine` (Lagrange3rd) as the fractional-rate-read
mechanism. This implementation instead uses a hand-rolled 4-point,
3rd-order Lagrange interpolator (`readGlitchRingBufferFractional()` - the
exact same closed-form cubic-Lagrange formula
`DelayLineInterpolationTypes::Lagrange3rd` implements internally) reading
directly from the already-captured, static `glitchRingBuffer` at an
arbitrary fractional index. Reasoning: `juce::dsp::DelayLine`'s API models
"continuously push live input, pop back after a settable delay TIME" - it
has no "seek/scrub to an arbitrary position within an already-captured
static buffer" operation, which is exactly what these three modes need
(their read position is a function of ELAPSED TIME within the event,
computed in closed form, not a fixed/slowly-drifting delay time). Bridging
into DelayLine's push model would require copying `glitchRingBuffer`'s
content into a second buffer every sample - wasted work, a second
real-time-unsafe sizing question, for zero interpolation-quality benefit
over reading the identical 4-point-Lagrange formula directly. The resulting
interpolation ORDER matches plan.md's named component exactly; only the
delivery mechanism differs. `juce::dsp::WindowingFunction` (Granular
Repeat) remains genuinely in use as specified.

**Tape Stop/Tape Start ramp math (click-free-at-ramp-start/end, plan.md
test criterion):** rather than accumulating a per-sample rate multiply
(which would need extra per-channel-call-ordering-sensitive state), the
read position is computed as the CLOSED-FORM INTEGRAL of a linear rate ramp
over elapsed samples within the current cycle (`elapsed`, derived from the
already-shared `glitchCurrentCycleLengthSamples`/`glitchCycleSampleCounter`
- no new per-sample accumulator needed, and independently/identically
computable by each channel's call): Tape Stop `rate(t)=1-t/T ->
position(t)=t-t^2/(2T)`; Tape Start `rate(t)=t/T -> position(t)=t^2/(2T)`
(T = the event's captured window length = the full cycle length for these
two modes). This is mathematically identical to accumulating
`position += rate` every sample from t=0, but is exactly reproducible/
stateless and C1-continuous (both position AND its derivative are
continuous functions of t) - which is what makes the ramp genuinely
click-free, not just "no instantaneous jump" but "no instantaneous jump in
the rate of change either." Both formulas reach `T/2` at `t=T` (the ramp
only ever traverses half the window's nominal length over its full run,
since it spends the other half decelerating/accelerating) - a designed
consequence of the linear-rate assumption, not a bug.

**Pitch Jump interval set (architecture.md does not pin down a specific
interval set - flagged, this implementation's own resolution):** a fixed
musical-interval ratio set, `kGlitchPitchJumpRatios` = {1/2, 2/3, 3/4, 4/3,
3/2, 2} (octave/fifth/fourth down and up), chosen ONCE per event via
`glitchRandom.nextInt(6)`. UNISON (1.0) is deliberately OMITTED so this
mode always produces an audibly distinct "jump," directly addressing
plan.md's test criterion ("Pitch Jump produces correct musical intervals").
Playback is CONSTANT-rate (non-ramping) at the chosen ratio,
`position(t) = t * ratio`, wrapped modulo the window length with the SAME
linear loop-edge fade convention Tier-1 already uses at every wrap.

**Shared (non-per-channel) vs. per-channel state - the other significant
design decision this phase introduced:** Tier-1's existing per-channel
arrays (`glitchWindowReadPos[2]`) work because each channel's call
independently computes an IDENTICAL deterministic result even though it's
computed twice (once per channel-call per sample) - safe for a plain
increment, or (Retrigger) a pure function of already-shared state. That
pattern is UNSAFE for anything that (a) draws from `glitchRandom` at wrap
time (would consume/produce DIFFERENT values per channel, breaking stereo
coherence and doubling RNG draw count per wrap) or (b) advances a shared
index that must move exactly once per wrap, not twice (Slice/Random
Slice's slot advance; Random Repeat's re-selection). For Granular Repeat's
grain-voice scheduler and Slice/Random Slice/Random Repeat's wrap-triggered
state changes, the advance is computed exactly ONCE per SAMPLE (not once
per channel-call) via two new helpers -
`advanceGlitchGranularVoicesForThisSample()` /
`advanceGlitchTier2SharedState()` - called from `processBlock()`'s outer
per-sample loop (mirroring the existing cycle-boundary bookkeeping's own
shared-once-per-sample placement, immediately after `glitchMixAmt` is
computed, guarded by `glitchWantsWet`). `readGlitchWindowSample()`'s
per-channel calls for these modes then only READ the already-resolved
shared position (`glitchTier2SharedReadPos`/`glitchSliceCurrentIndex`/
`glitchGrainVoices`), never advance it themselves.

**RNG draw-sequence invariant (carried forward from Phase 3.5, reaffirmed
unchanged by this phase):** the two UNCONDITIONAL per-cycle-boundary draws
(length jitter + probability jitter/Bernoulli trial) still happen every
cycle boundary regardless of mode/bypass - that structural invariant is
untouched. Tier-2 modes needing EXTRA draws (Granular Repeat's per-grain-
spawn position; Random Slice's one-time shuffle; Pitch Jump's one-time
interval choice; Random Repeat's per-wrap re-selection; Noise Burst's
per-sample noise) all draw strictly WITHIN that mode's own active/wet
playback window - only after the current cycle's boundary draws already
happened, and only while that specific mode is both selected AND actively
playing. This does not violate the invariant (cycle-boundary draw
COUNT/STRUCTURE per cycle stays mode-independent) - it does mean a
session's overall `glitchRandom` stream position (and therefore the exact
VALUES of later cycle-boundary draws) will differ depending on which modes
were active in between, which is expected/unavoidable for any shared
single-stream PRNG and is consistent with Phase 3.5's own reproducibility
claim (identical seed + identical mode/parameter automation over time ->
identical output; not "identical regardless of what mode happened to be
selected").

**Granular windowing implementation note:** `juce::dsp::WindowingFunction`
does not expose its internal table for arbitrary per-sample random-access
reads (only a bulk `multiplyWithWindowingTable()` operating on a
caller-supplied array). So `glitchGrainWindowFn` is used exactly ONCE, in
`prepareToPlay()`, to bake a Hann shape into an all-ones
`glitchGrainWindowTable` (`std::vector<float>`, sized once from
`kGlitchGrainLengthMs`, never resized in `processBlock()`) via that bulk
call; `processBlock()` then does plain indexed lookups into the baked
table - correct and real-time-safe.

**Real-time safety:** `glitchGrainWindowFn.fillWindowingTables()` and
`glitchGrainWindowTable`'s sizing/baking both happen ONLY in
`prepareToPlay()`. All Tier-2 per-sample work (grain-voice bookkeeping,
closed-form position math, 4-point Lagrange reads, quantization, noise
draws) is bounded, allocation-free, lock-free arithmetic over
already-allocated state - the same real-time-safety posture Phase 3.5
established. No new locks, file I/O, or unbounded loops were added (the
grain-voice loop is a fixed `kGlitchGranularVoiceCount` = 3 iterations; the
Fisher-Yates shuffle is a fixed `kGlitchSliceCount` = 8 iterations, and
only runs at event setup, not per-sample).

## Phase 3.5 Details

**Ring buffer (`glitchRingBuffer`, stereo `juce::AudioBuffer<float>`):**
allocated once in `prepareToPlay`, sized per architecture.md's "4 bars at
slowest supported tempo" guidance (`kGlitchMinSupportedBpm` = 40bpm, 4/4 time
assumption) computed against the ACTUAL prepared sample rate (not a hardcoded
192kHz), plus one block's headroom. Written continuously with the incoming
post-Bitcrush signal every sample, regardless of whether a glitch is active or
`graphBypassGlitch` is on (architecture.md: "so there's always a recent-
history window available to capture from when a trigger fires"). Never
resized/reallocated in `processBlock()`.

**Trigger mechanism:** a free-running per-sample cycle counter
(`glitchCycleSampleCounter`) whose period derives from `glitchBufferLength`
(1/64..4 bars) converted to samples via host BPM
(`AudioPlayHead::getPosition()->getBpm()`, JUCE 8 `std::optional` API;
falls back to 120bpm with no host/no tempo info, real-time-safe, no
allocation in the fallback path). At every cycle boundary, a Bernoulli trial
(seeded `glitchRandom`, gated by `glitchProbability`) decides whether an
event fires. NOT phase-locked to the host's bar/beat grid - a deliberate
scope simplification (architecture.md only specifies BPM-derived sample-count
conversion, not PPQ phase-locking), flagged as a reasonable interpretation.

**Chaos formula (exact):**
```
chaosNorm = chaos% / 100
probJitter   = (2*rand()-1) * chaosNorm * 0.3   (+/-30% of probability at chaos=100%)
lengthJitter = (2*rand()-1) * chaosNorm * 0.5   (+/-50% of cycle length at chaos=100%)
effectiveProbability = clamp01(glitchProbability%/100 + probJitter)
thisCycleLength = clamp(nominalCycleLengthSamples * (1 + lengthJitter), 1, ringBufferCapacity - 4)
```
Both jitter draws + the Bernoulli draw happen from `glitchRandom`
UNCONDITIONALLY every cycle boundary, regardless of `glitchMode`/
`graphBypassGlitch` - the RNG draw sequence depends only on tempo/sample-
rate/probability/chaos, never on mode selection or bypass state.

**RNG seeding + persistence (architecture.md: "must use a seeded
juce::Random instance... seed stored in custom state"):** `glitchRandom` is a
private, non-global `juce::Random` member. `juce::Random::getSystemRandom()`
is used exactly ONCE, in the constructor (message thread, one-time entropy
source), to generate the initial seed stored in
`glitchRandomSeedAtomic` (`std::atomic<juce::int64>`). `prepareToPlay` and
`processBlock` (once per block, per architecture.md's Thread Boundaries
convention "read once per relevant trigger event, not per-sample") apply
this atomic's current value to the real `glitchRandom` instance whenever it
changes. Persistence: `getStateInformation` writes the seed as a String XML
attribute (`glitchRandomSeed`, full int64 precision - `XmlElement`'s integer
attribute API is 32-bit only) plus a `corruptrStateVersion` attribute onto
the APVTS state's root element (not a second nested ValueTree - sufficient
at this phase's scope, matches architecture.md's "version attribute... from
day one" advice); `setStateInformation` restores it into the atomic (missing/
corrupt attribute -> fresh system-RNG seed, never crashes, per
architecture.md's Restore Behavior). **How a user reloading a saved preset
gets identical glitch timing:** the exact same seed value round-trips through
save -> XML attribute -> load -> atomic -> next block's `glitchRandom`
reseed, so the sequence of Bernoulli-trial/jitter draws from that point
forward is bit-for-bit identical across sessions - the RNG STREAM is
reproducible; exact wall-clock/transport-position alignment of those draws
still depends on where playback starts, same as any tempo-synced effect.

**Per-mode window semantics + design differentiation:** Stutter = short
slice (1/8 of cycle length) captured once, looped forward. Repeat = full
cycle-length window captured once, looped forward. Reverse = full window,
read back-to-front every pass. Freeze = very short (~15ms, "single-cycle"
approximation) window captured once, looped forward. Silence = hard-gated
mute (`readGlitchWindowSample` returns 0.0f), no ring-buffer read. Retrigger
= short slice (1/4 of cycle length) but, UNLIKE Stutter/Repeat, RE-CAPTURED
fresh from the current ring-buffer write position at the start of EVERY loop
pass rather than held fixed for the whole event - a deliberate design
decision (architecture.md groups Stutter/Repeat/Retrigger/Micro Loop
together without specifying what distinguishes them) giving Retrigger a
live, rhythmically-gated re-sync character distinct from Stutter/Repeat's
fixed-loop character. Flagged here per the task's request to document any
such resolution.

**Click-free guarantees (plan.md Phase 3.5 Test Criteria):**
1. Window entry/exit + graphBypassGlitch toggling mid-window: shared
   `glitchActiveMixSmoothed` (`juce::SmoothedValue`, 4ms ramp) blends
   dry<->wet, advanced once per sample in the outer loop (matching this
   file's established channel-shared-SmoothedValue convention).
2. Loop-back discontinuities (every mode's internal loop point):
   `readGlitchWindowSample` applies a linear fade-in/fade-out (3ms,
   sample-rate-derived `glitchLoopEdgeFadeSamples`) at the START and END of
   EVERY pass through the window, not just the first.
3. Mode switching mid-playback: detected once per block (matching this
   file's established `lastFilterTypeIndex` change-detection pattern) -
   forces the current cycle to end immediately and restarts cycle timing
   cleanly under the new mode, which drives the mix envelope to 0 and ramps
   cleanly to dry via mechanism #1, even if a window was mid-playback at the
   moment of the change.

**Real-time safety:** `glitchRingBuffer` allocated once in `prepareToPlay`,
never resized in `processBlock()`. `glitchMinWindowSamples`/
`glitchFreezeWindowSamples`/`glitchLoopEdgeFadeSamples` precomputed
(sample-rate-derived ints) in `prepareToPlay`, no float->int conversion of a
sample-rate constant per-sample. `juce::Random::nextFloat()` calls and
`AudioPlayHead::getPosition()` (once per block, stack-based
`std::optional`) are both allocation-free. No locks, file I/O, or unbounded
loops added.

**Validation performed (methodology + limitation):**
This agent session had no Bash/execution tool available (Read/Write/Edit
only - same constraint the Stage 1 foundation-shell-agent session flagged).
No `tests/` directory or Catch2/JUCE `UnitTestRunner` harness exists
anywhere in this repo (checked other plugins, e.g. KICKR - none found), so
per the task's fallback instructions this phase was validated
**analytically/mathematically** rather than by executing a compiled test
harness:

- Per-sample loop gain bound: the only two elements affecting amplitude
  around the recirculation path are the damping filter (a stable one-pole
  TPT lowpass, magnitude response <= 1.0 at every frequency, unity only at
  DC) and `internalGain = 0.85 * tanh(feedbackAmount/100)`. Since
  `tanh(x)` is bounded in [-1, 1] for every finite real `x` (including
  out-of-spec automation edge cases), `internalGain` is bounded in
  [-0.85, 0.85] unconditionally - independent of `feedbackAmount`,
  `feedbackDamping`, or sample rate. At the parameter's actual UI ceiling
  (`feedbackAmount = 100%`), `tanh(1.0) = 0.7616`, so the real worst-case
  per-pass gain is `0.85 * 0.7616 = 0.6474 < 1`.
- Worst case identified per the test criteria (max feedback, min damping):
  `feedbackDamping = 0%` maps to an 18kHz cutoff (near-transparent, gain
  ~1.0 across most of the audible band), so the bounding case reduces to
  the gain analysis above: per-pass loop gain ~0.6474, a contraction
  mapping (ratio < 1). This is a convergent geometric series for ANY finite
  input, at every `feedbackAmount` x `feedbackDamping` combination in the
  full 0-100% x 0-100% range - steady-state output is bounded by
  `x_max / (1 - 0.6474) approx 2.84 * x_max`, finite for any finite input.
  The independent RMS-envelope limiter (0.95 threshold) provides a second,
  unconditional hard ceiling on top of this.
- NaN/Inf recovery: traced every operation in the per-sample chain
  (`tanh`, `std::pow` with a fixed positive base, `FirstOrderTPTFilter`
  with a Nyquist-clamped positive cutoff, multiplication, `std::sqrt` of a
  non-negative accumulator) - none can produce non-finite output from
  finite input under this design. The only realistic NaN/Inf source is a
  corrupted/non-finite sample arriving via the host's `x` input (e.g. a
  misbehaving upstream plugin) or a deliberately-injected test value. Both
  are caught: guard (1) catches corruption already present in
  `loopSample`/loop state; guard (2) catches a non-finite `x` that would
  otherwise leak through `x + loopSample` even after guard (1) resets the
  loop's own state to zero. Both guards fire and recover within the same
  sample they're detected in (bounded to one sample, well within "one
  block").
- No throwaway/temporary debug code was added to the shipped source (no
  execution harness was possible to write given the tool constraint, so
  none needed removing).
