## Reconciliation Notes (draft -> locked)

- **Source of truth for scope, positions/types/ranges:** `v5-ui.yaml`'s 69 UI controls (56 unique bound APVTS parameters - some controls are dual-binding pairs sharing one parameter, see Dual-Binding Pairs below).
- **Source of truth for DSP-purpose descriptions, ranges/defaults of pre-existing parameters:** `parameter-spec-draft.md`, carried over verbatim where the parameter id matches and the mockup's range/default agrees (all matching ids agreed - no conflicts found).
- **7 controls the v5 mockup notes flagged as NEW** (not yet in the draft) are added below as new bool/float parameters using the semantics documented in `v5-ui.yaml`'s `notes` section: `graphBypassSaturation`, `graphBypassWaveshaper`, `graphBypassFilter`, `graphBypassBitcrush`, `graphBypassGlitch` (module bypass toggles: Bool, default `false`, `true` = bypassed), `microDelayTime` (Float, feedback-loop delay time), `sequencerEnabled` / `modMatrixEnabled` (Bool, default `true`, `true` = module on - **opposite polarity** from the bypass toggles above).
- **8 additional NEW parameters** not explicitly flagged by name in the mockup's summary notes but required to bind the per-LFO Shape/Sync controls visible in the Mod Matrix strip: `lfo1Shape`/`lfo1Sync` through `lfo4Shape`/`lfo4Sync` (8 total). `parameter-spec-draft.md` only described `lfo1Rate` through `lfo4Rate` as a shared group without individually declaring Shape/Sync as APVTS parameters; `architecture.md`'s resume notes explicitly flagged "per-LFO shape/sync x4" as architecture-required but not yet in the draft - this locked spec resolves that gap using the mockup's actual bound `parameter`/`choices` values.
- **6 draft-only parameters not bound to any v5 UI control** — `tone`, `bias`, `distortionMix`, `sampleRateReduction`, `chaos`, `xyPadSmoothing` — were deferred in v1. **As of v2, these ARE included** in this locked spec as confirmed MVP-scope architecture requirements (product decision, 2026-09-02): they still lack a bound control in the v5 mockup (`UI Control` on each reads "Not yet bound to a mockup control - architecture-required, pending future mockup iteration"), but Stage 1 must implement their APVTS parameters now so DSP/automation work isn't blocked on a future mockup pass. A future mockup iteration should add bound controls for them.
- **32 Mod-Matrix-slot parameters** (8 slots x source/destination/amount/enable, per `architecture.md`'s "Mod Matrix's 8 slots ARE APVTS parameters" decision) were deferred in v1 because the v5 mockup's `mod_matrix_grid` is a decorative `matrix-grid` visual element (source x destination grid with amount dots), not 8 individually-bound UI controls. **As of v2, these ARE included** in this locked spec as confirmed MVP-scope architecture requirements (product decision, 2026-09-02): each of the 32 (`modSlot1Source..modSlot8Source`, `modSlot1Destination..modSlot8Destination`, `modSlot1Amount..modSlot8Amount`, `modSlot1Enable..modSlot8Enable`) still lacks a bound control in the v5 mockup (same `UI Control` note as above), but Stage 1 must implement their APVTS parameters now. A future mockup iteration should add bound controls for them (or a decision to keep the matrix-grid purely decorative with routing set via a dedicated per-slot editor panel).

## Total Parameter Count

**Total:** 94 automatable parameters (40 Float, 26 Bool, 28 Choice).

- v1 (mockup-bound): 56 automatable parameters (26 Float, 18 Bool, 12 Choice).
- v2 addition (architecture-required, not yet mockup-bound): 38 automatable parameters (14 Float, 8 Bool, 16 Choice) = 6 draft-only (`tone`, `bias`, `distortionMix`, `sampleRateReduction`, `chaos`, `xyPadSmoothing` — all 6 Float) + 32 Mod Matrix slot parameters (8 slots x [`Source` Choice, `Destination` Choice, `Amount` Float, `Enable` Bool] = 16 Choice, 8 Float, 8 Bool).
- v2 total: 56 + 38 = 94 (26+14=40 Float, 18+8=26 Bool, 12+16=28 Choice).

## Dual-Binding Pairs (same parameter, two controls)

Established pattern (carried from v2 onward, see `v5-ui.yaml` header notes): a base control (always visible) plus an ADV-revealed "fine-adjust" mirror control bind the SAME parameter, not two parameters:

- `filterCutoff`: base `filter_cutoff_detail` knob + ADV-revealed `node_filter_cutoff` fine knob
- `glitchProbability`: base `glitch_probability_detail` knob + ADV-revealed `node_glitch_probability` fine knob

## Parameter Definitions

### Module: Top Bar / Global

### qualityMode

- **Parameter ID:** `qualityMode`
- **Type:** Choice
- **Choices:** ECO, NORMAL, HIGH, EXTREME, AUTO
- **Default:** "NORMAL" (index 1)
- **UI Control:** Top bar combo dropdown, 5 choices (ECO/NORMAL/HIGH/EXTREME/AUTO).
- **DSP Usage:** Oversampling factor applied around the nonlinear stages (Distortion, Bitcrush/SRR, and the feedback loop's nonlinear element) to control aliasing. User-selectable CPU/quality tradeoff, not hidden. Concrete AUTO heuristic is an open Stage-2 research item (architecture.md spec gap).
- **Automation:** Supported

### Module: Distortion

### graphBypassSaturation  *(NEW in v5)*

- **Parameter ID:** `graphBypassSaturation`
- **Type:** Bool
- **Range:** Off / On
- **Default:** Off (`false`)
- **UI Control:** Distortion module's top-left power/bypass icon-button (24x24, power-icon glyph).
- **DSP Usage:** Module-level bypass for the Distortion stage (the distortionAlgorithm engine). true = stage is fully bypassed (dry passthrough of that node in the signal-flow graph); false (default) = stage is active. One of 5 new v5 per-module bypass toggles rendered as the module's top-left power icon.
